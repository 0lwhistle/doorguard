## 0. 项目定位(一句话)

**RK3576 平台嵌入式人脸识别门禁整机自研**:从 Buildroot 固件裁剪、DTS 使能屏幕与触摸、交叉编译工具链搭建,
到 NPU 人脸识别链路、LVGL 无桌面 UI、SQLite 业务存储、Vue3 Web 上位机与 OTA A/B 升级,
一个人打通"固件 → 驱动 → 算法 → 应用 → 上位机"全栈。6 天 83 次提交,3.2 万行 C 代码(含测试)+ 2.4 千行前端,
28 个自动化测试全绿,核心性能指标在真板上实测。

## 1. S — Situation(情境)

### 硬件与环境

| 项 | 内容 |
|---|---|
| 开发板 | KickPi K7(RK3576,6 TOPS NPU,4×A72 + 4×A53) |
| 屏幕 | 5 寸 MIPI F050008M01(720×1280,GT9xx 电容触摸,I2C 0x5D) |
| 摄像头 | IMX415(800 万像素,MIPI CSI)+ RKISP + rkaiq 3A |
| 官方 SDK | Rockchip rk3576-linux-2026091008(19GB,kernel 6.1 + buildroot) |
| 编译机 | 单台 Ubuntu VM,8 核 / 内存仅 7.2G(编译须 `make -j6` 防 OOM) |
| 开发机 | WSL(编码/交叉编译/单测) + VM(固件全量编译),代码只经 git 流转 |

### 痛点与动机

1. **官方 SDK 交付的是通用示例,不是产品**:weston 桌面 + RKADK 多媒体 demo,既跑不动业务,
   也不满足"开机即出界面、掉电配置不丢、远端可运维"的门禁机要求。
2. **人脸功能没有可用底座**:SDK 自带的 ROCKIVA 方案在本版快照里**缺 rk3576 人脸模型文件**
   (`rockiva_data_rk3576` 只有前级检测件,人脸件仅存在于 rk3588/rv1126 目录),需走厂商渠道补包。
3. **约束**:编译机内存小;单目 RGB 无深度信息(活体只能做动作指令式);19GB SDK 不能进 git,
   必须与业务代码仓库严格隔离。

## 2. T — Task(目标与任务)

1. 把通用 Linux SDK **裁剪为无桌面门禁固件**(去 weston/chromium,加 LVGL+DRM、SQLite、dropbear、GStreamer)。
2. 在官方人脸模型缺失的前提下**自建 NPU 人脸识别链路**(检测 + 识别 + 1:N 检索 + 1:1 比对)。
3. 实现完整门禁业务:用户管理(上限 2000)、刷脸 1:N、管理员 1:1、密码/指纹/IC 卡多因子、
   动作活体、开门日志、Web 上位机、OTA A/B 升级、NTP 校时、mDNS 局域网发现。
4. **质量可验证**:每个功能模块必须"代码 + 测试 + README + 使用示例"齐全(缺一不算完成),
   纯逻辑测试必须在 PC 宿主 gcc 上可跑,不允许只靠板子联调。

## 3. A — Action(关键行动)

### 3.1 固件与平台层

- 从零编写 `doorGuard` 专用 Buildroot defconfig:裁掉桌面栈,启用 LVGL(DRM 后端)、
  rkaiq 相机引擎、rknpu2、RGA、SQLite、dropbear(SSH/SFTP)。
- **改 DTS 使能屏幕**:K7 设备树原本未 include 任何屏,需加 5 寸屏 dtsi(含 GT9xx 触摸节点),
  内核重编 + dtb 反查节点验证。
- 自建交叉编译工具链(gcc-arm-10.3 + **与固件同源 sysroot**,避免 libc 版本冲突),
  封装 `dg-build` / `dg-deploy -r <IP>` / `dg-serial` 三个脚本(串口为 1500000 8N1,非默认 115200)。
- **SDK 改动管理**:所有 SDK 修改在独立 git 分支,经 `git format-patch` 导出到业务仓库的
  `sdk-patches/`,保证换机/重建 VM 时"原版 SDK + `git am`"即可复原。

### 3.2 架构设计(架构 v2：评审通过并落地)

- **五层栈**:`ui → services → modules → drv ← components`,外加 `proto/` 作为唯一横切契约层。
- **依赖白名单**约束跨层调用(违规不予合入);模块/服务间**只经事件总线通信**,
  仅对"高实时/高性能只读路径"开放直调,且必须**登记制**(初始仅登记数据库特征快照、配置读取两项)。
- **自研四个机制组件**(把 ESP32 模板的接口形态移植到 pthread,只取概念不搬 ESP-IDF 依赖):
  - `tasker`:≤500ms 短任务 + 周期/次数任务,三分级 lane;
  - `event_bus`:独立分发线程的异步总线,`EV_<域>_<动作>` 命名;
  - `holder` / `registry`:**双注册表**,统一状态机 `REGISTERED → INITIALIZING → READY/ERROR/DISABLED`,
    带依赖检查(防循环)、必须项失败拒绝启动、可选项失败降级为 DISABLED。
- **看门狗与降级矩阵**:`main` 装配完成后转为看门狗,5s 周期巡检服务心跳;
  可选服务超时 → 重启一次 → 失败则禁用并通知 UI;**必须服务**(显示/触摸/sqlite)超时 → 安全停机。
  降级矩阵使得"摄像头或 NPU 失效时自动禁用刷脸,但密码/IC 卡照常可用"。
- **线程规范**:每线程 = 原子状态位 + 阻塞原语(condvar 超时等待),先置位后 signal;
  **明令禁止仅凭标志位忙等**(会丢唤醒);所有等待必须带超时兜底;建立线程↔服务归属表,
  耗时任务一律独立线程(解决 tasker 队头阻塞),OTA 用按需线程(完成即退出)。

### 3.3 视觉链路(项目技术核心)

- **驱动层** `drv/npu/`:rknn 运行时薄封装(全仓唯一 `#include <rknn_api.h>` 的文件)+
  RGA letterbox 预处理与 ROI 裁剪(坐标数学在头文件内联,可单测)。
- **算法层** `rknn_face.c`:**RetinaFace 与 SCRFD 双解码器**、NMS、5 点仿射对齐、余弦比对、
  归一化;纯 C 实现,**可脱离硬件在宿主机单测**。
- **服务层**:**可插拔后端契约**——`rknn`(自组主线)/ `rockiva`(官方备选)/ `sim`(PC mock)
  三个实现共用同一 `vision_backend_ops_t` 契约,支持配置或环境变量按名切换。
  **换后端不改服务层、状态机、UI、存储一行代码**——这是该契约的核心价值。
- **数据流做到"帧只拷一次"**:ISP → RGA → NPU / DRM 全程零拷贝(dma-buf),CPU 不碰像素。
  检测每帧跑、识别按 300ms 节流,特征库(≤2000 条)启动后**全量载入内存** + RWLock 保护,
  **禁止每帧查库**。
- **fail-closed 安全设计**:发布命中前必须校验特征口径一致性(`model_tag`),
  不一致时**宁可不开门,不可错开门**;换了识别模型 = 换了特征空间,旧特征立即屏蔽。

### 3.4 业务与应用层

- **认证状态机**(`services/access/auth_fsm.c`):纯 C **注入式状态机**——UI/服务层把摄像头、
  识别、触摸、定时器全部翻译成事件喂进来,FSM 内部不碰 LVGL、不碰数据库,只通过回调输出动作。
  覆盖 `NORMAL / ADMIN_AUTH / MENU / VERIFY / RESULT / STANDBY` 六状态与
  `输入ID / 选方式 / 1:1人脸 / 指纹 / 密码 / IC` 六个验证子步。
  含三个易错细节的处理:**定时器 seq 失效**(每次重置 +1,旧定时器事件按 seq 丢弃)、
  **密码连错锁定**、**管理员人数为 0 时菜单免认证进入**(避免管理员被删光后菜单永远进不去的"鸡生蛋"问题)。
  因为不碰 UI/DB,全部边界(超时/重复/取消)都能用事件序列在 ctest 里逐条驱动。
- **密码安全**:PBKDF2-SHA256 + 盐存储,不存明文;连错 N 次锁定。
- **存储**:SQLite(WAL),`users` / `access_logs`;分页查询前后各预加载两页;
  特征缓存增量同步、fail-closed;**`access_logs` 的唯一写入方是 access 服务**(保证日志出口唯一)。
- **门控**:GPIO 继电器脉冲(时长可配),引脚配置来自 `default.json`,代码零魔数。
- **UI**:LVGL 8.3 直跑 DRM(无 X11/Wayland),预览软渲染 27fps。**VOP2 双平面硬件合成
  (NV12 dma-buf 直送 Overlay plane,30fps 零 CPU)已完成设计、硬件探针与全套实现并上板,
  因 LVGL8.3 透明层"擦除语义缺失"(残影)回退待启用——计划迁移 LVGL9.5 后重启**,
  实现与硬件探针结论见 git f519b1e。主页弹窗式验证流、待机页、菜单、用户编辑页(添加/编辑同页、全字段、缺项显示"无")、
  门禁记录查询页。UI 层只收发事件、不做业务决策;外部线程一律 `lv_async_call()` 回 UI 线程。
  文案全量 i18n(`_()` 包裹 + zh-CN/en-US 语言包),并有测试拦截漏翻与字体缺字形。
- **网络族**:Web 上位机(内嵌 civetweb + Vue 3 前端,**详见 §3.5**);
  OTA 应用级 A/B 升级(流式接收 / 断点续传 / 双重 sha256 / 槽位原子切换 / 失败自动回滚,
  **详见 §3.6**)、NTP 校时(门禁日志可信度依赖时间)、mDNS 局域网发现(自实现 wire 格式 + 防重名)。
- **配置**:`default.json` 模板(只读)+ 设备 `/userdata/doorguard/cur_config.json`(运行只读它);
  原子写(临时文件 → fsync → rename)+ 500ms 防抖落盘;配置放数据分区,
  使 A/B 升级与重刷固件不丢用户配置。

### 3.5 Web 上位机(嵌入式设备自带的完整管理面)

- **形态**:civetweb 单库编译进固件 + Vue 3 前端,**构建产物转 C 数组一起烧进 rootfs**
  (`vite build` → `pages/` → `gen_pages.sh` → `web_pages.c`)。设备上电即用,
  **不需要外网、不需要额外服务,固件构建机也不需要 node**。后端 C 约 1,577 行,前端 2,359 行 / 35 文件。
- **8 个接口**:`POST /api/login`、`POST /api/logout`、`GET /api/device`(版本/时长/用户数/日志数/IP/联网/mDNS/NTP/存储)、
  `GET /api/logs`(from/to/user_id/page 分页)、`POST /api/ntp`(异步 202,结果走 WS)、
  `POST /api/account`(改账号/口令)、`POST /api/ota/upload`(流式收包 + sha256)、`GET /api/ws`。
- **三条安全约束**(都是踩过坑后的选择):**改状态的接口一律 POST**(方法不符回 405——
  原先 GET 也能触发 NTP 校时,错误面过宽);**WebSocket 的 token 走查询串**(浏览器无法给 WS 加自定义头);
  **未授权的 WS 连接必须显式回 401 再拒**(否则客户端只看到连接被关,分不清"口令错"与"断网")。
- **WebSocket 推送模型重构**:原实现靠客户端每 2s 发 `ping` 触发连接线程排水,
  **本质是用轮询掩盖跨线程写的不安全**;改为常驻 `ws_pusher_thread` 出队后广播,
  安全性靠两个条件**同时**成立——civetweb 的 `mg_websocket_write` 内部持 `mg_lock_connection`
  使写不交错,且推送线程**持连接表锁**做整轮写入、而连接销毁必须先进 `ws_close` 摘表项,
  因此写期间连接不可能被释放。队列满时计数丢弃而非阻塞业务线程;推送线程刷心跳供看门狗判活。
- **鉴权与风控**:凭据存 `device_config`——账号明文(展示用)+ **PBKDF2-SHA256 盐/哈希(10000 迭代)**,
  不存明文、不落日志;首启生成 `admin/admin` 并置 `pwd_default` 标志提示改密;
  **改凭据即吊销全部会话**;**登录风控**同来源连错 5 次锁 60 秒(429 + `Retry-After`),
  锁定表内存维护、重启解锁(防局域网脚本爆破,又不把管理员永久锁在门外)。
  账号口令合法性**与设备端共用 `proto/valid.h` 同一份规则**,菜单与上位机两个入口不漂移。
- **前端分层纪律(用工具强制执行,不是口号)**:`views → stores → api → components` 四层,
  `frontend_check.py` **扫源码并拒绝**"组件里 import store""store 里 import 组件""api 之外出现 fetch";
  样式色值只允许用 `tokens.css` 变量,且**与设备端 `ui/theme.h` 同源**(上下位机看起来是同一个产品);
  前端用 hash 路由,路由守卫接管 401 跳登录。
- **交付面校验**:`pages/` 与 `web_pages.c` 是**入库的产物**,忘了重新生成会被静态检查拦下;
  `web_test.sh` 还会校验服务端吐出的字节与仓库里那份**逐字节相同**;体积预算卡在
  app.js ≤300KB / app.css ≤60KB(实测 131KB / 14KB)。
- **测试密度是项目里最高的**:vitest **44 项**(api/stores/组件/路由守卫/401 跳转)、
  **`bundle.spec.js` 把将编进固件的 `pages/assets/app.js` 真实字节直接丢进 jsdom 执行**,
  跑通"挂载 → 登录 → 概览 → WebSocket 事件上屏";另有 `web_test.sh` **62 项断言**
  (自动起 PC 模拟器打真接口:鉴权与方法约束、日志过滤/分页边界、NTP 异步 + WS 主动推送、
  改密、OTA 闭环、登录风控)、`frontend_check.py`(资源表一致/MIME/路由对照/分层纪律/体积预算)
  与 ws / mDNS 协议测试。
- ⚠️ **已知边界**:监控画面页仍是占位(远程预览链路未接);前端文案只有中文(设备端 i18n 未覆盖前端);
  Web 端按规格不开放用户管理。详见 §6。

### 3.6 OTA A/B 升级(接收 → 校验 → 槽位 → 自愈,上板实测)

**三层结构,每一层职责单一:**

- **接收层 `ota_service.c`(406 行 C)**:
  HTTP 流式收包**内存占用 O(8KB)**(边收边落盘,不整包进内存);manifest 走请求头
  (`X-OTA-Version/-Size/-SHA256/-Offset`);**大小预检**(超限开始前拒绝);
  **断点续传**(偏移与已暂存字节数不符 → 409 重传);**独立写盘线程**与 HTTP 收包解耦
  (有界缓冲 + 两个 condvar:生产者等空位、消费者等数据);**进度事件**
  `EV_NET_OTA_PROGRESS`(≥5% 一拍 + 终态)经事件总线广播,上位机实时可见;
  sha256(OpenSSL EVP **流式**)不符 → 422 拒收,通过 → rename 为 staged(校验闭环)。
- **板端 sidecar `S60doorguard`(158 行 bash)**:
  **应用级 A/B 双槽**——`/root/dg_app.A` 与 `dg_app.B`,`/root/door-guard` 是指向当前槽的
  符号链接;监听循环检测到 staged 包 → 完成判定(大小 2s 不变)→ **sha256 二次复核**
  (应用侧已验一次,落地前再验)→ 拷入**非活动槽** → symlink **原子切换**
  (`ln -sf` 临时链接 + `mv`)→ 拉起新版本。
  **自动回滚**:监督循环发现新版本 **15s 内退出且连续 3 次** → 自动切回另一槽。
- **主机工具**:`dg-ota-upload <IP> <包> [版本]` 一键推送。

**两个实测教训进 sidecar 的细节**(这两个坑不加防护,OTA 在真板上会失灵):

1. exec 失败(rc=126/127)时**跳过相机 3A 服务重启**——坏包快速重启循环里
   反复拉起 rkaiq 曾把 ISP 驱动搅到内核崩溃(实测);
2. 监督循环**必须完全脱离会话**(重定向到 /dev/null)——继承 ssh 的 stdout 时,
   会话一断,子 shell 往死管道写即被卡死,监督循环假死、**回滚失灵**(实测)。

**实测结果**:有效包 A↔B 切换正常运行;**坏包秒退 3 次后自动回滚成功**;
槽位化在重启后自愈(读符号链接决定启动槽)。测试:test_ota(ctest)+
web_test.sh OTA 闭环断言(正常包 200 / sha 不符 422 / 超大小 400)。

**边界(见 §6)**:当前是**应用级 A/B**(rootfs 内双槽文件 + symlink),
**分区级 A/B(分区表 + uboot bootcount/altbootcmd 回退)是方案未实施**;
staged 包放 `/tmp`(tmpfs)重启即失;只有 sha256 完整性校验、无签名。

### 3.7 工程方法论

- **文档纪律**:`PROJECT_PLAN.md` 唯一事实来源、`DEVLOG.md` 记录过程与坑、
  `DEV_HANDBOOK.md` 沉淀硬件实测结论;收尾必写日志 + 同步实测结论。
- **边界优先**:实现任何功能前先列边界情况(空输入/超时/重复/权限不足/并发/掉电恢复),
  每个错误显式处理并返回失败码,**禁止静默吞掉**。
- **测试策略**:**28 个 ctest 用例**全部在 PC 宿主 gcc 可跑(含 1:N/1:1 流程、认证 FSM、
  配置、存储、i18n、事件总线压力、OTA、mDNS wire、RKNN 解码数学、NPU letterbox 坐标数学、
  录入链路端到端);另有 PC 模拟器宿主,使 UI/FSM 链路**不接硬件即可开发调试**。
- **PC/板端解耦**:`#ifdef` 只允许出现在 HAL 的 sim 后端与 main 装配处,业务代码零条件编译。

## 4. R — Result(结果,均为板上实测)

### 4.0 没完工怎么写 R(本项目约 2/3,先读这节)

**简历的 R ≠ 项目完工。R = 截至今天,你能拿证据说话的结果。** T 写全量目标、R 只认领
已验证的部分——STAR 的结构本身就容纳"项目在进行中"。三条原则:

1. **每个 R 句都用"已实测/已跑通/测试全绿"锚定**。数字全部出自板上实测
   (检测 6.7ms、识别 56ms、28 测试全绿、OTA 回滚实测),附录 B 可复现——
   这些是真的,与项目完工与否无关。
2. **没做完的功能不是"写了但没做好",而是"不进简历"**。活体判定算法、指纹/IC 卡、
   远程视频预览——这些在上面的条目里**一个字都不出现**。简历只承诺你写的每个字,
   删掉没把握的,不是撒谎,是划界。
3. **进度用"分期"口头讲,不说"完成 2/3"**。完成度百分比对读者无意义(2/3 的分母他不知道),
   而且自我贬损。被问"项目做完了吗",标准答案:

   > "项目分三期:**一期是核心识别链路,已上板闭环验收**——固件、架构、NPU 检测识别、
   > 基础业务、Web 管理面、OTA 都在真板上实测过;**二期是活体判定和多因子硬件接入,进行中**;
   > 三期做产品化(分区级 A/B、只读 rootfs、升级签名)。"

   主动这么讲**反而加分**:说明你清楚边界、有路线图,而不是被追问出来才承认。

**雷区词对照**(写简历/面试时自查):

| ❌ 不能说 | ✅ 换成 |
|---|---|
| 整机交付 / 项目完成 | 整机软件栈从零搭建并上板运行 |
| 支持活体检测 | 活体为强制管线阶段,状态机已就绪,判定算法是下一阶段 |
| 支持指纹 / IC 卡 | 多因子接口已抽象,硬件接入是二期(当前可用:人脸 + 密码) |
| 支持远程实时预览 | Web 面覆盖概览/记录/账号/OTA,实时画面未接 |

### 4.2 三个"无报错但全错"的坑(最有含金量的部分)

1. **模型目标平台不匹配**:官方 `RetinaFace.rknn` 实为 **RK3588** 模型,
   本板 NPU 驱动直接拒收(`This rknn model is for RK3588`)。须按 rk3576 + int8 重转才通。
2. **识别模型未烤归一化(最隐蔽的一个)**:ArcFace 直接喂 uint8 会让**所有 embedding 高度相似**
   ——cos(脸, 纯色图) ≈ 0.79 —— 结果识别永不命中,而**整个链路没有任何报错日志**。
   根因是输入必须为 `(x-127.5)/127.5` 的 **F32 预归一化**;修正后 cos(同人, 变暗)=0.98、
   cos(脸, 纯色)=0.11,一眼可辨。
3. **LVGL 事件 user_data 语义误用**:`lv_event_get_user_data(e)` 返回的是**回调注册时**的
   user_data(列表行为 NULL),而非 `lv_obj_set_user_data` 设置的对象数据;导致编辑页拿到空 uid
   → 误判为"新增模式" → 全字段显示"无"、保存必因 ID 为空而失败。
   修正为 `lv_obj_get_user_data(lv_event_get_target(e))`。
   同日还揪出 `db_user_update` 的"len=0 表示保留"部分更新语义**无法表达清除**,
   为此新增 `db_user_clear_face()`。

> **这三条的共同价值**:都是"表面正常、静默失效"型缺陷,排查靠的是构造最小对拍实验
> (离线跑模型比对分数、逐层打印中间结果),而不是靠猜。每一条都补了回归测试并写入项目文档沉淀。

### 项目里最值得讲的三个"决策"

1. **fail-closed**:特征口径不一致时宁可不开门——安全系统的默认姿态应是"拒绝"而非"放行"。
2. **可插拔后端契约**:官方方案(Rockchip ROCKIVA)因缺模型文件而不可用时,
   架构上能从"自组 rknn"平滑切换过去、且**换后端不动业务一行代码** ——
   这个契约在关键路径上救过场,是很好的架构设计案例。
3. **注入式状态机**:FSM 不碰 UI/DB,把线程、定时器、渲染全部外置为回调,
   代价是接口设计成本,收益是**全部业务边界可单测**——门禁的超时/重复/取消逻辑如果只能上板点,是灾难。

## 附录 C — 高频追问预演:civetweb 还是 mongoose?为什么自实现 mDNS/NTP?

**先摆事实**:本项目用的是 **civetweb**(HTTP + WebSocket,单库 MIT);mongoose 虽在
`third_party/mongoose/` 但零引用、不参与编译,是残留死重。

### 两者渊源与区别

CivetWeb 是 Mongoose 的社区分支:mongoose 原为 MIT 开源,2013 年前后 Cesanta 转为
GPLv3 + 商业双授权,社区从最后一个 MIT 版本 fork 出 CivetWeb 延续 MIT 独立发展。

| 维度 | civetweb | mongoose |
|---|---|---|
| 协议 | **MIT**(商用闭源无义务) | **GPLv3 + 付费商业授权**(传染性) |
| 并发模型 | 阻塞式,**每连接一线程**(池) | 单线程事件循环,handler 不可阻塞 |
| 功能面 | 专注 HTTP/1.1 + WebSocket | 全家桶:另带 DNS/SNTP/MQTT/raw TCP+UDP(新版含 mDNS) |
| 长连接成本 | 占线程池名额(故代码有 `WS_MAX_CONN` 限流) | 每连接一个小结构,海量空闲连接低成本 |
| 适用形态 | 局域网管理面、个位数客户端 | 海量并发连接的 IoT 遥测类场景 |

**部署视角的结论**:本设备 Web 面是"局域网 + 个位数浏览器客户端 + 内存资源表静态页 +
REST + 每页签一条 WS + 偶发 OTA 流式上传"。此形态下两者**功能等价**,区别在代码形态:
civetweb 的阻塞模型让 OTA 上传写成"handler 里循环读 body 写盘"的直线代码;
mongoose 则要拆成"socket 可读即读一块"的回调链。mongoose 的容量优势在本场景用不上。

### 为什么选 civetweb(按权重)

1. **协议**:门禁要产品化,GPL 传染性对闭源固件是硬伤——基本一票定终身;
2. **线程模型同构**:全项目 pthread 多线程架构,"每连接一线程、可阻塞"与其世界观一致;
3. **设计依赖其行为**:WS 推送模型安全推理的两支柱之一,就是 civetweb 的
   `mg_websocket_write` 内部自带连接锁、跨线程写不交错;
4. 事件循环的容量优势在个位数客户端场景为零。

**付出的学费**(可主动讲):`NO_SSL=1` 下它在 OpenSSL 3 环境 WebSocket 握手必崩
(不包含 OpenSSL 头却调 `EVP_Digest`,缺原型 → 指针截断成 int → 段错误;自身 `-w`
把告警压光),以 `dg_openssl_shim.h` + CMake `-include` 补原型解决。

### mDNS/NTP 为什么不在 Web 服务器里做?

**civetweb 做不了**——它只是 HTTP/1.1 + WebSocket 服务器,无 UDP。mDNS(UDP 5353
多播 DNS)与 NTP(UDP 123)都在其协议面之外。项目的分层选择:

- **mDNS 完全自实现**:`mdns_wire.c`(DNS wire 编解码:A/PTR/SRV/TXT、名字压缩)+
  `mdns_responder.c`(UDP 5353 组播、QU 位决定组播/单播应答、cache-flush 位、
  探测重名自动改名 doorguard-2、SRV 的 target A 放 additional 段省一轮往返、
  TTL 分级 120s/4500s)。几百行 C,**与 avahi-browse 实机对拍通过**,手机可直连发现。
- **NTP 不实现协议、只做编排**:板端 rootfs 自带 chrony,`ntp_service` 执行
  `chronyc burst 4/4 + waitsync 10`;先 ping 探测联网,未联网明确失败不重试到死,
  结果经事件总线广播到 WebSocket。

**面试收尾句**:civetweb 管"人看的那一层"(HTTP/WS);mDNS/NTP 是"设备发现与校时"
的协议层,本就不该由 Web 服务器承担——按协议分层、每个协议选最小的实现,
mDNS 自实现几百行且有实机对拍,好过为一个功能引入 GPL 全家桶。
